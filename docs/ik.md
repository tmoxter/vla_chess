# Inverse kinematics

`pixi run ik-report` regenerates this file. Every number below comes from that run on this host; none are estimates.

## Method

`kinematics.IKSolver` wraps `mink`'s differential IK: a frame task on the `gripperframe` site (position cost 1, orientation cost 1, Levenberg-Marquardt damping 0.001), a posture task toward the resting pose (cost 0.001), and a freezing task holding every dof that is not one of the five arm joints. Joint limits are a constraint inside the QP rather than a clamp applied afterwards. Each iteration solves the QP and integrates the result at a timestep of 1, with the per-iteration joint step capped at 0.5 rad, for at most 40 iterations.

A solve counts as converged when position error is within 2 mm **and** orientation error within 0.05 rad. Both are always reported: five joints cannot satisfy a general six-dof pose, so orientation is an objective the solver trades against position, and a caller that only needs position should read the numbers rather than the flag.

## Round trip, warm started

500 poses generated by forward kinematics from random in-limit configurations, each solved from a seed perturbed by up to ±0.3 rad per joint.

| | |
|---|---|
| Converged | 500/500 (100.0%) |
| Median iterations | 2 |
| Median solve time | 3.14 ms |
| 95th percentile solve time | 4.51 ms |
| Worst position error | 2.00 mm |

Criteria: ≥ 98% converged, and a median solve ≤ 5 ms so that IK does not become the bottleneck next to rendering.

## The seed matters, and the iteration budget does not

The same round trip solved from the resting pose instead of from near the answer.

| Seeded from | Converged | Median iterations |
|---|---|---|
| Within ±0.3 rad of the answer | 500/500 (100%) | 2 |
| The resting pose | 316/500 (63%) | 9 |

Differential IK is local. The cold-start shortfall is not slow convergence that a larger `max_iterations` would fix — those solves have settled into a minimum that does not reach, and raising the budget changes nothing. That is what `solve_from_restarts` is for, and the same reason `grasp.VerticalGraspSolver` restarts. Along a trajectory the previous configuration is the seed, which is the first row.

## Reference grasp poses

The board-surface poses in `assets/reference_grasps.json`: near the shoulder, where the arm doubles back over itself, and the only poses in this project confirmed by eye to be grippable.

| Seeded from | Recovered |
|---|---|
| The resting pose | 30/30 |
| Within ±0.3 rad of the answer | 30/30 |
| Restarts, up to 8 | 30/30 (median 1 attempt) |

These come back cold, which is worth stating plainly because an earlier revision of this solver recovered only 18 of the 30 and the natural reading was that board-surface poses are the hard region. They are not: that was the posture task set two orders of magnitude too heavy, pulling every solve toward the resting pose hard enough to miss. The table below is what settled it, and the resting pose being a good seed for these particular targets is also why this section is easier than the one above it.

## Why the posture task is weighted where it is

Round trip as above, at each posture cost.

| Posture cost | Converged | Median iterations |
|---|---|---|
| 0.01 | 72/200 (36%) | 40 |
| 0.001 | 200/200 (100%) | 2 |
| 0.0001 | 200/200 (100%) | 2 |
| 0 | 200/200 (100%) | 2 |

Five joints against a six-dof target leaves almost no nullspace for a posture preference to occupy, so the posture task does not bias a free direction — it competes with the frame task directly. The default is set from this table, not from a convention.

## What this does and does not establish

Every pose measured here is either generated by this arm's own forward kinematics or taken from the reference grasps, so a clean sheet means the solver agrees with the model it was given. It says nothing about whether that model's geometry matches a real SO-101 and a real board — the same open question `docs/reachability.md` records, unchanged by this step.

It also says nothing about self-collision: `solve` will return a pose that reaches the target through the arm's own body. Screening is the caller's job, via `solve_from_restarts(accept=...)` or `collision.contacts_at_pose`.
